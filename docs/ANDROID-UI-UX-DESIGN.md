# Android UI / UX 设计规范

## 目标

Android 客户端的主体验应当像成熟的 GPT 聊天客户端一样轻松、清楚、容易上手，同时保留 Codex 作为代码 Agent 的专业能力。借鉴 ChatGPT Android / 移动端的交互规律，不复制其品牌标识、专有图标、视觉素材或逐字文案。

核心原则：**聊天内容是页面主角，项目与工具是随手可用的上下文，Agent 执行过程可读、可展开、可审批。** 不要把首页做成传统管理后台，也不要把每一条消息和每一个事件都塞进相同的 Card。

## 可以借鉴的移动端模式

- **简洁的会话导航**：用可随时打开、切换会话后自动收起的侧边抽屉/浮层承载历史会话、搜索、最近项目和设置入口；主聊天区不长期被复杂菜单占据。
- **输入区集中工具入口**：附件、项目文件、图片、MCP 工具、Skills 和其他输入能力集中放在输入框旁的“+ / 工具”菜单或底部抽屉中；默认只露出最常用的操作，避免一排按钮挤占聊天空间。
- **对话优先的内容布局**：消息自然连续排列，用户消息、Agent 回复和执行事件使用不同的视觉层级；长内容和工具日志按需展开。
- **流式响应与即时反馈**：Agent 回复可以边生成边显示；连接中、执行中、等待审批、已完成、失败和中断等状态在当前对话内明确呈现。
- **移动端输入体验**：输入区固定在底部并适配软键盘、横屏和安全区；支持多行编辑、附件预览、复制/编辑消息和清晰的发送/停止操作。
- **项目与会话组织**：历史会话易于搜索和恢复；项目/工作区作为上下文入口，而不是永远占据屏幕的长路径文本。

ChatGPT 的移动侧栏简化、输入工具收纳，以及 Android 输入区和附件交互的改进可作为公开交互参考，具体以官方更新说明为准：
https://help.openai.com/en/articles/6825453-chatgpt-release-notes

## 本项目建议的信息架构

### 1. 聊天主页面

- 默认打开聊天页；顶部只保留导航入口、当前会话标题/新建入口，以及必要的连接状态。
- 当前项目显示为紧凑的上下文标签，可点击切换或查看完整路径；不要长期展示大块“当前 Agent 状态”卡片。
- 模型、推理强度、权限/运行模式和会话目标放进精简选择器或上下文设置底部抽屉。常用状态可显示为小标签，详细设置按需展开。
- 会话历史、搜索、已归档会话、项目入口和服务商设置从导航抽屉进入；切换会话后抽屉自动关闭并回到聊天。
- 不要用底部导航把每个低频设置都做成一级页面。终端可以保留明确的快捷入口；服务商、MCP、运行环境和 Root 设置归到工具/设置区域。

### 2. 消息与执行过程

- 用户消息使用轻量气泡/右侧对齐样式；Codex 回复采用连续的正文排版，不要每段都套一个大卡片。
- 正文需要支持 Markdown 标题、列表、表格、引用、链接和代码块；代码块提供复制、选择和横向滚动等操作。
- 命令执行显示为紧凑的活动条目：命令、工作目录、运行状态、退出码和耗时；详细 stdout/stderr 默认折叠，点开后可复制或继续查看。
- 文件修改显示文件列表、增删概览和 Diff 预览；能区分新增、修改、删除文件。不要只把文件路径拼成一段普通文本。
- 计划、MCP 调用、子任务和其他工具事件显示为不同类型的可展开活动项；同一个事件的 started / delta / completed 状态应更新同一条目，不能重复刷出大量新卡片。
- 最终总结与中途执行记录分层展示；保留可追溯的工具过程，但默认不要让日志淹没最终答案。

### 3. 输入区（Composer）

- 输入框固定在聊天底部，圆角、足够高、支持多行和长文本；内容滚动不应把输入区挤走。
- 输入框旁提供“+”入口，打开底部抽屉，按类别列出：添加文件/图片、选择项目文件、调用已启用 MCP 工具、选择 Skills，以及当前真正支持的其他输入方式。
- 输入区上方可显示已附加文件、当前项目、模型等紧凑标签，并允许移除或调整。
- 空闲时显示发送；Agent 执行时保留追加指令能力，并单独提供明显的停止按钮。发送、追加指令、停止不能混成一个含义不清的按钮。
- 语音输入只有在 Android 端实现并经过权限、隐私和真机测试后才显示；不能为了模仿参考应用先摆一个无功能麦克风按钮。

### 4. 权限审批和风险提示

- 审批请求应在聊天时间线中突出显示，包含请求动作、命令或工具、目标路径/设备、工作目录、风险说明和当前权限范围。
- 操作按钮只根据锁定版本 Codex App Server schema 提供；没有实现的审批类型明确提示并安全拒绝，不能假装支持。
- 对 Root、进程附加、Hook/注入、系统文件写入等操作额外展示目标和影响范围，并要求用户逐次明确授权。
- 审批卡片不允许被普通日志折叠或隐藏；在用户处理前，持续显示任务正在等待确认。

### 5. 终端与工程工具

- 终端仍是独立 PTY 页面，有真实终端网格、快捷键、复制粘贴和会话管理；不要把终端伪装成聊天消息。
- 聊天与终端共享所选项目工作区，但 Agent、普通 PTY 和 Root PTY 保持独立进程与权限身份。
- 项目文件浏览、Git 状态、Diff、构建/测试结果、Logcat 和 APK 分析应优先以结构化面板或可展开结果呈现，并能回到对应会话上下文。

## 视觉和可用性要求

- 采用 Material 3 组件体系，优先清晰、克制的浅色/深色主题；颜色只用于状态、风险和重点，不要给每个普通消息块上色。
- 保证长对话滚动顺畅；流式输出时避免频繁抖动布局，用户手动滚动查看旧消息时不要强制拉回底部。
- 适配小屏手机、横屏、分屏、系统字体缩放、软键盘和手势导航安全区；主要触控目标应便于拇指操作。
- 长按消息应支持选择/复制；可编辑的用户消息要明确显示编辑状态；代码与命令应易于复制。
- 网络断开、服务商错误、运行环境未安装、模型不兼容和审批等待应使用口语化中文说明下一步怎么做，避免只显示原始异常字符串。
- 动画只用于反馈，不影响性能和可访问性；提供语义标签、对比度和键盘操作支持。


## 侧边栏与 Agent 工作区参考

侧边栏不应成为一整页设置面板。手机默认使用约 **300dp** 的临时会话抽屉；主要空间留给聊天。抽屉内部按“新建 / 项目 / 会话 / 工具与设置”组织，会话列表独立滚动，常用导航采用约 40dp 的紧凑条目，低频设置放到底部或二级页面。用户选中会话或切换到其他页面后，抽屉应立即收起。

已核对以下开源实现，借鉴交互模式而非复制源码：

- **RikkaHub**：`ChatDrawer.kt` 使用 `ModalDrawerSheet(Modifier.width(300.dp))`，将顶部动作和会话列表分开布局，并使用 LazyColumn 管理会话浏览；可参考其移动端会话历史组织方式。源码：[ChatDrawer.kt](https://github.com/rikkahub/rikkahub/blob/master/app/src/main/java/me/rerere/rikkahub/ui/pages/chat/ChatDrawer.kt)。
- **Operit**：`NavigationComponents.kt` 把常用导航压成 40dp 高的紧凑项目，`DrawerContent.kt` 将主要功能分组、固定底部快捷入口；可参考分组和低频功能收纳。源码：[NavigationComponents.kt](https://github.com/AAswordman/Operit/blob/main/app/src/main/java/com/ai/assistance/operit/ui/main/components/NavigationComponents.kt)、[DrawerContent.kt](https://github.com/AAswordman/Operit/blob/main/app/src/main/java/com/ai/assistance/operit/ui/main/components/DrawerContent.kt)。
- **OpenCode**：窄屏使用临时侧栏 / 面板，并允许独立设置面板宽度；移动端选中会话后必须关闭侧栏，避免内容被抽屉遮住。参考：[GUI 面板布局文档](https://opencode.ai/docs/build/plugins/gui)、[移动端侧栏行为问题与修复讨论](https://github.com/anomalyco/opencode/issues/37746)。

RikkaHub 使用 AGPL-3.0、Operit 使用 LGPL-3.0、OpenCode 使用 MIT。此处仅参考可观察到的布局和交互原则；不复制其代码、图标、资源或专有文案。引入任何源码前仍需单独审查许可证和兼容义务。

## 实施优先级

1. **先整理聊天页骨架**：简化顶部、增加会话导航抽屉，把模型/推理和项目上下文收紧，固定底部输入区。
2. **再改消息渲染**：用户气泡、Markdown Agent 回复、可展开命令/工具活动、独立文件 Diff 视图。
3. **完善输入工具抽屉**：附件预览、项目文件、MCP/Skills 入口；只接入已经实现的能力。
4. **打磨审批、历史会话和工程工具面板**：明确风险和状态，保留详细过程。
5. **最后做 Android 实机验收**：软键盘、长消息、流式输出、旋转屏幕、暗色主题、触控与性能。

每个阶段都要单独构建并记录未完成项。仅完成静态 UI 不代表对应功能已经连通 Codex App Server 或 Runtime。

## 消息复制、编辑与重发

消息操作属于聊天页基础能力，不应等用户提出后再临时补按钮。

- 用户消息、助手回复和可展开执行记录都应有易找到的“更多”菜单，至少支持复制；助手和用户正文同时支持 Android 原生文本选择。
- 复制默认保留可见正文和 Markdown 源内容，不得复制 API 元数据、内部消息 ID、协议字段或隐藏状态标记。等 Markdown 渲染器接入后，再提供“复制 Markdown / 复制纯文本”两种格式。
- 用户消息支持“编辑并重发”。编辑历史消息不是把文本追加到同一会话末尾：必须按 Codex App Server 的轮次边界创建新分支，从被编辑轮次之前的最后一轮继续；旧会话和旧回答必须保留。
- 仅当消息内容能被完整重建时才允许编辑。带图片/文件/技能附件，或同一个 turn 内有多条 user 消息的情况，暂时隐藏编辑入口并说明原因，不能把附件静默丢掉。
- 助手回复支持“重新生成回答”，通过其对应的可编辑纯文本用户消息建立分支；执行中的轮次、审批等待状态和没有明确来源消息的活动记录不能重新生成。
- 创建分支或发送失败时保留用户草稿，且不删除原会话。长历史需要分页完整定位目标轮次和恢复分支历史。
- 活动项和助手/用户消息是不同类型；复制执行信息时要包含命令、工作目录、状态、退出码和已有输出。

## 首次服务器/模型引导与对话时间显示

- 首次准备好 ARM64 私有运行环境后，如果还没有 Codex Agent 默认服务商，显示两步引导：先填写 Responses API 服务器地址、API Key、模型 ID 和可选自定义请求头，再连接服务器读取模型目录并选择模型。
- API Key 与自定义请求头继续通过 Android Keystore 加密保存。引导完成后才进入主界面；保存过的服务器和模型在后续启动时自动恢复。
- MCP 页面只保留 MCP 专属操作，不放置服务商设置快捷按钮。
- 聊天输入框与发送按钮必须保持同一行；文本输入区占据主要宽度，发送按钮使用稳定宽度，工具和回车模式放在第二行。
- 用户消息和助手消息显示时间；助手回复结束后显示本轮实际耗时。历史时间优先使用 Codex App Server 的 `startedAtMs` / `completedAtMs`，若服务端未记录则不显示伪造的历史时间。正在进行的轮次按 `turn/started` 与 `turn/completed` 事件计算耗时。
