# Root 权限与逆向 / 动态调试架构

## 产品用途

本客户端主要用于在 Android 设备上调用 Codex 完成代码编写、项目构建、问题定位、应用分析和动态调试。调试对象应是用户自己的设备、自己开发的应用，或用户明确获得测试授权的应用与系统。

Root 是可选的设备级能力，不是安装或使用 Codex 客户端的前提。没有 Root 时，普通聊天、代码编辑、私有运行环境和普通 PTY 仍应工作；只有系统级文件、进程、调试和设备操作才要求对应权限。

## 三种身份必须分开

| 通道 | 运行身份 | 用途 | 默认状态 |
|---|---|---|---|
| Codex Agent / App Server | Android 应用 UID | 代码分析、修改、构建、测试、项目内命令和会话管理 | 正常启用 |
| 普通 PTY 终端 | Android 应用 UID | Bash、Git、编辑器、构建工具和交互式命令 | 用户主动启动 |
| Root PTY / 设备调试通道 | 经 Root 管理器授权的 root UID | 设备级日志、系统目录、进程和调试能力 | 默认关闭，逐次申请 |

**严禁为了让 Codex“权限更大”而直接以 root 启动整个 codex app-server 或普通 Agent 进程。** Agent 仍在应用 UID 下运行。只有用户在终端页主动申请 Root、系统 Root 管理器明确授予后，才允许建立独立 Root PTY。普通终端和 Root 终端不能共享进程、stdin/stdout 或权限状态。

Root 管理器对授权的最终决定权高于 App 内的开关。用户可以随时在 Magisk、KernelSU 或其他兼容管理器中撤销授权；下一次启动 Root 终端前必须重新验证。

## 当前已接入的 Root 入口

- RootAccessManager 只在用户点击“申请 / 重新检查 Root 授权”时查找并执行 su，通过 su -c id -u 验证实际 UID；找不到 su、用户拒绝、超时和执行异常分别显示状态。
- 启动 Root PTY 前再次检查授权，避免只依赖上次打开页面时的旧状态。
- Root 终端使用现有独立 PTY 与私有 Bash，工作目录限定在应用当前已验证的项目目录。
- JNI 接口通过 argv 参数数组传递程序及参数，不把命令文本拆成可执行文件参数；Root 启动脚本只包含应用生成的路径，并对路径进行 shell quoting。
- Root 启动链不继承 LD_PRELOAD，避免把 Termux exec helper 注入 root 进程；私有 PREFIX、HOME、CODEX_HOME 和项目目录仍明确设置。
- 不保存“永久 Root 模式”，页面内开关只控制当前会话的启动身份；每次启用 Root 终端都重新校验。

当前只完成 Root 授权探测、终端页入口和独立 Root PTY 启动接线。尚未完成 Android 真机上的 Magisk / KernelSU 兼容性、退出清理、SELinux 行为和长时间运行测试；**尚未把 Root 能力接入 Codex Agent 工具调用**。

## Agent 调用 Root 工具的后续设计

后续如需让 Codex 在聊天中请求设备级调试工具，必须新增独立的 Root Tool Gateway，而不是把 Agent 进程切换成 root。Gateway 应采用显式授权请求：

1. 每个工具声明动作类型和资源范围，例如 device.logcat.read、process.maps.read、package.inspect、debugger.attach、system.file.write。
2. 默认策略为 **每次询问**；明确拒绝优先于允许；没有规则时不能默认放行。
3. 审批卡显示设备、目标包名 / PID、具体命令、工作目录、读写范围和可能影响。用户确认的是本次明确动作，不是笼统的“给 AI Root 权限”。
4. 第一阶段只做逐次允许 / 拒绝。以后如增加“本项目始终允许”，必须限定到具体 action、resource、项目和有效期，不能用 root:* 或通配符把设备控制权限一次性全开。
5. 拒绝或撤销后，正在等待的请求应取消；Root 子进程和进程组应可停止；权限失败要以结构化结果返回，不能静默降级成普通身份继续执行。
6. 记录必要的审计信息：何时、哪个会话、哪个工具、对什么目标执行、退出码和结果摘要。敏感内容与密钥必须脱敏；不要把 Root 输出写入普通日志后无条件上传。

此设计借鉴 OpenCode 的 action/resource 规则、通配匹配与最后匹配胜出、拒绝优先、待审批请求生命周期，以及 once / always / reject 审批结果；也参考其项目级保存授权和 hard-deny policy。OpenCode 自带的基础权限配置包含较宽泛的 allow 规则，因此我们不照搬其默认权限，而是为 Root 操作采用更严格的默认 ask，初期只允许逐次确认。另借鉴 Operit 的 Root / Shizuku / 普通 Shell 分层和“自动允许、每次询问、禁止”权限交互；不复制它们的运行时或源码。Codex 的工具调用协议仍按本项目锁定的 App Server schema 接入。

## 逆向与动态调试工具路线

按风险从低到高分层，先做只读信息，再做需要授权的进程调试和写操作：

- **代码与构建**：私有终端中的 Git、编译器、测试框架、静态分析和构建日志；优先在项目工作区执行。
- **应用 / APK 分析**：包信息、版本、签名证书、Manifest、资源和 DEX 检查；APK 反编译或重打包工具作为可选组件，必须锁版本、校验来源和许可证。
- **设备诊断**：Logcat、设备属性、进程列表、包安装信息、服务 / Activity 状态；逐项区分普通 Android 权限、ADB / Shizuku 和 Root 能力。
- **运行时观察**：在系统允许的范围读取进程状态、映射和日志；访问其他应用私有目录、附加进程、读取内存或修改系统状态必须额外审批。
- **动态调试**：评估 GDB / LLDB、Frida 等工具的 ARM64 Android 兼容性和分发许可。调试器附加、注入、Hook、修改进程状态和写系统目录均属高风险动作，必须显示目标进程 / 包名并逐次确认；不提供隐蔽驻留、绕过用户授权或对未授权目标操作的功能。
- **设备级修改**：系统文件写入、模块安装、属性修改、服务启停和应用强制停止单独列为高风险权限，默认拒绝或每次明确询问，并支持停止与恢复说明。

Root 并不等于无限制权限：SELinux、Android 版本、内核配置、厂商策略和目标进程隔离仍可能阻止 ptrace、内存访问或系统修改。不能因取得 UID 0 就把某项调试功能标记为必然可用。

## 验收要求

- 无 Root 设备仍可正常使用聊天、私有运行时、普通 PTY 和项目工作区。
- 未点击申请前，不启动 su，不探测 Root 授权，不创建 Root 进程。
- Root 管理器拒绝、没有 Root、超时、授权撤销和 su 路径失效时均有清晰提示。
- 普通 Agent 进程始终是应用 UID；Root PTY 才显示 root 身份。
- Root PTY 的启动、输入、Ctrl+C、停止、应用退出和异常退出均清理子进程；不能留下孤儿进程。
- 在至少一种 Magisk 和一种 KernelSU 环境上分别测试；记录 Android 版本、管理器版本、SELinux 状态、实际 UID 和进程退出结果。
- 所有动态调试工具只在自有或明确授权的目标上验证；审批拒绝必须真正阻断操作。
